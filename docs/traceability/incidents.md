# Trazabilidad consolidada de siniestros (M4)

Consolidación de INC-INTEGRATE-M4-20261013 para la cadena requisito → contrato → implementación → prueba → evidencia. Las etiquetas de fuente del BRD/SRD v0.2 se conservan; que algo esté implementado no convierte una propuesta en requisito confirmado. Lo diferido está marcado **pendiente** y no cuenta como implementado. Este documento no declara G4 aprobado.

## Brechas contra el texto del paquete, con su razón

- Los journeys por API cubren cada ruta con los pasos que la API real permite sin completar una orden de taller: el journey de aceptado resuelve desde `insurance_process` y no pasa por `repair` con la orden cerrada. El paso a `repair` con órdenes terminadas, costos de la orden y evidencia final está en `tests/e2e/fleet/incident-costs.test.ts` y `e2e/incidents-real.spec.ts` (acceptance 11); no se repite aquí.
- Sin seguro: la ruta llega a `repair` con una orden vinculada; el presupuesto `clean` como alternativa a la orden se verifica en las pruebas de dominio de `workflow` (`service.test.ts`, `process.test.ts`).
- Ciclos de SLA de la reapertura con métricas separadas: cubierto por la suite de SLA (`incident-sla-scenarios.ts`); J5 verifica los dos ciclos de cierre.
- Matriz de aislamiento: no incluye tenant suspendido, sesión revocada ni cambio de permisos con un job de SLA pendiente como casos propios; esos casos tienen prueba en `tests/integration/platform` (`negative.test.ts`, `sessions.test.ts`, `jobs.test.ts`).
